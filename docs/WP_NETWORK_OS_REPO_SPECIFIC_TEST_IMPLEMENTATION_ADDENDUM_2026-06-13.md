# 3. Provider-mode architecture

West Peek Network OS must expose three explicit provider modes:

- `fixture`
- `local-adapter`
- `live-provider`

No test may silently change modes.

## 3.1 Fixture mode

Purpose: deterministic unit and mocked browser proof.

Rules:

- no external Gmail or Sheets calls
- immutable checked-in fixtures
- deterministic clocks and IDs where required
- no production secrets
- safe in assistant containers and CI

## 3.2 Local-adapter mode

Purpose: local full-stack proof using production-shaped adapters backed by isolated local stores.

Rules:

- same public interfaces as production adapters
- durable local readback
- support refresh/re-entry
- support duplicate and failure injection
- no production provider calls

## 3.3 Live-provider mode

Purpose: guarded Tier 4 proof against real Gmail, Google Sheets, and deployed Cloudflare runtime.

Rules:

- explicit command only
- vault-test or approved live-provider secret profile
- unique proof run ID
- provider evidence capture
- mandatory cleanup in `finally`
- incomplete cleanup blocks proof completion

# 4. Fixture-backed Gmail adapter

## 4.1 Required interface

The fixture adapter must implement the same application-facing operations as the live Gmail adapter:

- list eligible messages
- fetch message details
- return headers and MIME parts
- expose mailbox identity
- expose Gmail message ID and thread ID
- simulate provider errors
- simulate malformed payloads
- simulate repeated delivery

The application must select the adapter through an explicit provider factory, not scattered environment checks.

Recommended contract:

```ts
interface GmailProvider {
  listMessages(input: GmailListInput): Promise<GmailMessageRef[]>;
  getMessage(input: GmailGetInput): Promise<GmailMessage>;
  getMailboxIdentity(): Promise<MailboxIdentity>;
}
```

## 4.2 Required fixture behaviors

The fixture adapter must support:

- one clean plain-text message
- one HTML-only message
- one multipart alternative message
- one quoted reply chain
- one attachment-only pitch
- one malformed sender envelope
- one missing RFC Message-ID
- one repeated Gmail message ID
- one provider timeout
- one provider permission error
- one rate-limit response

## 4.3 Parity law

Fixture behavior must match the production adapter’s normalized application contract. Tests may not assert fixture-only fields or bypass production parsing logic.

# 5. Fixture-backed Google Sheets adapter

## 5.1 Required interface

The local adapter must implement the production-facing operations used by the application:

- read canonical snapshot
- append row
- batch update rows
- create tab
- read headers
- repair headers
- write maintenance log
- list proof fixtures
- archive or clean proof fixtures

Recommended contract:

```ts
interface SheetsProvider {
  readSnapshot(options?: { fresh?: boolean }): Promise<NetworkSnapshot>;
  appendRow(tab: CanonicalTab, row: Record<string, unknown>): Promise<RowRef>;
  updateRows(tab: CanonicalTab, updates: RowUpdate[]): Promise<void>;
  runMaintenance(input: MaintenanceInput): Promise<MaintenanceResult>;
}
```

## 5.2 Local durability

The local adapter must persist to an isolated test-owned file or database so Tier 3B can prove:

- write
- fresh readback
- refresh/re-entry
- duplicate prevention
- lifecycle transition
- cleanup

An in-memory-only adapter is insufficient for Tier 3B persistence proof.

## 5.3 Failure injection

The adapter must support deterministic injection of:

- permission denied
- missing spreadsheet
- missing tab
- malformed headers
- rate limit
- partial batch failure
- stale cached snapshot
- maintenance-log write failure

# 6. App-specific test authentication

## 6.1 Required test-auth mode

West Peek Network OS must have a deterministic test-auth provider isolated from production OAuth.

It must support:

- authenticated operator
- unauthenticated visitor
- expired session
- revoked session
- invalid state/nonce
- wrong callback origin
- logout and re-entry

## 6.2 Security boundaries

Test auth must not:

- accept arbitrary email headers as authentication
- use production OAuth tokens
- weaken production middleware
- expose a production-accessible bypass
- default on outside `test` runtime

## 6.3 Activation

Test-auth mode must require all of:

- `NODE_ENV=test`
- explicit `AUTH_PROVIDER=test`
- non-production hostname or test runner context

Production startup must hard-fail if test authentication is enabled.

## 6.4 Evidence

Tier 3B and Master Gauntlet diagnostics must record:

- auth provider mode
- test persona
- session creation result
- session persistence result
- logout/revocation result

No tokens or cookies may be stored in diagnostics.

# 8. Archive/restore and revoke/restore state contracts

## 8.1 Contacts

Allowed states:

- `active`
- `archived`

Archive must record:

- archived timestamp
- actor
- reason

Restore must record:

- restored timestamp
- actor

Rules:

- archived contacts do not appear in default active views
- archived contacts cannot be selected for new intake attachment unless explicitly restored
- historical relationships remain intact
- repeated archive/restore calls are deterministic and idempotent

## 8.2 Event forms

Allowed states:

- `active`
- `revoked`

Revoke must:

- stop new submissions
- preserve prior attendees and history
- expose an intentional inactive result
- record actor, timestamp, and reason

Restore must define whether the same public token is reused or regenerated. This decision must be recorded in `ARCHITECTURAL_DECISIONS.md`.

## 8.3 Approvals, notifications, and touchpoints

Every lifecycle entity must define:

- valid states
- valid transitions
- forbidden transitions
- idempotent repeated actions
- visibility in active and history views
- persistence/readback expectations

# 9. Google Sheets maintenance semantics

Maintenance must be non-destructive by default.

## 9.1 Permitted automatic changes

- create missing canonical tabs
- add missing canonical headers
- normalize supported boolean values
- normalize supported status values where mapping is unambiguous
- fill missing timestamps only when source evidence is sufficient
- append a maintenance report

## 9.2 Prohibited automatic changes

- delete rows
- merge contacts
- silently suppress duplicates
- overwrite conflicting values
- reorder data rows without explicit contract
- remove unknown columns

## 9.3 Duplicate behavior

Maintenance may detect and report duplicates. It must not silently delete or merge them.

## 9.4 Idempotency

A second maintenance run against the repaired spreadsheet must produce zero new repairs except a new run log entry.

## 9.5 Transaction and partial-failure behavior

The implementation must define:

- operation ordering
- per-step result reporting
- behavior when one tab fails after another succeeds
- safe retry semantics
- maintenance run ID

A generic `maintenance unavailable` message is forbidden.

# 10. Provider-specific cleanup

## 10.1 Gmail cleanup

Every live Gmail fixture must use:

- proof run ID in subject or header
- dedicated proof label where supported
- registered Gmail message ID

Default cleanup:

- remove proof label from active processing scope
- archive or relabel
- do not permanently delete

Permanent deletion is permitted only for a designated test mailbox and explicit destructive-cleanup mode.

## 10.2 Google Sheets cleanup

Operational tabs use append-only cleanup:

- set proof status to archived/cleaned
- record cleanup timestamp
- record cleanup run ID

Temporary maintenance tabs named exactly `__proof_<run_id>_<tab>` may be physically deleted after exact ownership verification.

## 10.3 Application cleanup

Proof fixtures must disappear from default operator views after cleanup while remaining auditable in history or cleanup reports.

## 10.4 Cleanup verification

The cleanup verifier must query every provider and application surface touched by the run. A local ledger entry alone is not sufficient proof.

# 11. Real persistence contracts

Every mutating workflow must define and test:

1. write request
2. provider acknowledgement
3. fresh provider readback
4. normalized application snapshot readback
5. browser refresh
6. browser re-entry
7. active/history visibility

## 11.1 Freshness contract

A read labeled fresh must bypass application cache and disclose:

- freshness requested
- freshness served
- source timestamp
- cache age

## 11.2 Success contract

No success toast or `200` response counts as persistence proof without readback.

## 11.3 Idempotency contract

Every provider write must define:

- idempotency key
- duplicate response
- retry behavior
- concurrent request behavior

## 11.4 Partial failure

The application must distinguish:

- provider write failed
- provider write succeeded but readback failed
- stale readback
- cleanup failed
- diagnostics failed

# 12. Master Gauntlet journey specifications

The lanes named in the master plan must be implemented as exact journeys.

## 12.1 Shared-inbox founder journey

1. Seed founder pitch fixture into `info@westpeek.ventures` provider lane.
2. Run sync.
3. Assert one pending Deal Flow Intake record.
4. Assert classification, score, and source mailbox.
5. Assert no Contact exists yet.
6. Refresh and re-enter.
7. Convert or attach through UI.
8. Assert durable contact/readback state.
9. Clean proof fixtures.
10. Verify zero active proof records.

## 12.2 Duplicate race journey

1. Seed one unique message.
2. Run simultaneous sync requests.
3. Assert exactly one canonical Intake row.
4. Assert all other requests report duplicate/conflict.
5. Fresh-read provider and UI.
6. Capture request IDs and ingestion evidence.
7. Clean and verify.

## 12.3 Maintenance journey

1. Create isolated malformed proof tabs/rows.
2. Run maintenance through operator UI.
3. Assert structured result.
4. Read provider state.
5. Run maintenance again.
6. Assert idempotency.
7. Clean proof tabs.
8. Verify cleanup.

## 12.4 Contact lifecycle journey

1. Create proof contact.
2. Archive through UI.
3. Assert removal from Active.
4. Assert presence in Archived.
5. Refresh/re-enter.
6. Restore.
7. Assert Active state and preserved history.
8. Clean and verify.

## 12.5 Event form lifecycle journey

1. Create proof event form.
2. Submit one proof attendee.
3. Revoke form.
4. Assert subsequent submission rejected intentionally.
5. Assert prior attendee preserved.
6. Restore according to token policy.
7. Assert new submission behavior.
8. Clean and verify.

## 12.6 Approval and notification journey

1. Create pending proof approval.
2. Assert notification created once.
3. Decide approval through UI.
4. Assert durable state and notification resolution.
5. Refresh/re-enter.
6. Clean and verify.

Each journey must capture diagnostics on failure and provider evidence on live success.
